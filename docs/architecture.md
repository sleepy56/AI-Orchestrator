# Runtime and storage decisions

## Current state

`orch init` creates `.orch/tasks.json` and `.orch/models.json`. The first file is the task graph; the second maps logical routes such as `sol-high` to provider model IDs, effort, enabled state, and user weight. `orch models add` can register another Codex model without a source change. An added model is disabled until explicitly enabled. Claude is represented in the registry and by an unavailable provider adapter; it cannot execute yet.

`orch run` uses fake workers by default. `orch doctor codex --timeout-seconds 60` checks the installed Codex CLI with a small read-only request. A live run first needs `orch worktrees base BRANCH COMMIT`, which pins the branch head to the current approved plan and checks revisions. `orch run --executor codex --check "npm test"` starts each ready Codex task in its own Git worktree and branch at that base or an integrated dependency base. Ready siblings can run concurrently. The worker receives task instructions, pinned document names, dependency commits, and selected reviewed lessons; Orch records lesson and Codex context IDs. The user check and approved executable task checks run in that worktree. Passing changes become task branch commits; the target branch remains untouched. `orch worktrees integrate TASK-001,TASK-002 --check "npm test"` merges task commits in a temporary worktree, runs the combined check, and reports conflicts, diff, revision, and merge target. A passing integration creates an exact merge action. After its approval, `orch worktrees merge ACTION_ID` fast-forwards the checked-out, clean target branch only if its head and integrated revision still match. Check commands run through the system shell in trusted local worktrees.

`orch knowledge add` stores project notes. The local `KnowledgeStorage` boundary persists a schema version 1 snapshot at `.orch/knowledge.v1.json` for a project and `$ORCH_HOME/knowledge.v1.json` (or `~/.orch/knowledge.v1.json`) globally. It imports legacy `knowledge.jsonl` records on access, leaves those logs untouched, and tracks imported lines so later appends are brought in once. Atomic snapshot replacement and a local lock protect concurrent knowledge writes. A changed or malformed legacy prefix fails migration instead of silently discarding data. Notes have stable IDs, a pseudonymous source project ID, optional source run ID, task category, timestamps, and review status. `knowledge review` approves or rejects a local note; `knowledge edit` resets review to pending; `knowledge promote` copies an approved generalized note into global scope with its source entry ID. The promotion guard rejects obvious paths, source filenames, commands, checks, and failure details, while human review must catch identifying prose. `knowledge remove` deletes current content and retains audit events with IDs, timestamps, state changes, and content hashes. `knowledge export` emits entries and audit metadata; project exports contain private data. Legacy logs remain untouched and may still contain removed data. Attempts retain timestamps, simulated/live label, route, result, and usage only in the project store. `orch history` reads project attempts. Live workers receive only approved notes. A future Neon sync adapter can implement the storage interface; current CLI and API paths do not make remote writes. Runtime routing uses task difficulty, risk, type and configured model weights. The read-only proposal command evaluates comparable live outcomes with supplied prices; it does not change runtime routing.

The cross-project boundary is the reviewed global note, not the source project's log. A destination project sees shared global lessons only when it uses the same Orch home; its retrieval combines those lessons with its own approved notes, caps selection at five, and explains each match. A validated live attempt creates a pending local candidate; matching outcomes add run and attempt evidence to that candidate, while simulated attempts cannot create one. The local API separates current retrieval from lesson IDs actually recorded in run events. Model proposals require versioned prices and comparable live outcomes with complete usage and latency; simulated attempts do not count. A manual alias changes the read-only CLI proposal's chosen alias while preserving the configured route as fallback. Existing version 1 model registries gain missing Luna tiers on load without replacing configured profiles, weights, or policy version.

Each `orch run` writes a project-local `.orch/runs.jsonl` event stream with a UUID run ID, per-run sequence numbers, timestamps, task transitions, route choices, attempts, validation results, and an explicit simulated/live mode. The writer syncs each event before returning. The event stream begins with the task snapshot and policy version so a reader can replay that run. Model weight changes advance the policy version. `orch serve` exposes the existing GET task, model, attempt-history, run-list, and run-event endpoints on `127.0.0.1`. It also accepts versioned local commands at `POST /api/commands`; `GET /api/commands` returns private local detail, while `GET /api/commands/shared` constructs an explicit safe metadata projection. The API does not itself trigger workers; the existing CLI run path still starts them.

## Why files now, SQLite for the product

JSON keeps editable plans and model settings easy to inspect and share. The versioned knowledge snapshot gives the CLI a migration path without a new dependency; run replay remains JSONL. These files are weak for cross-project queries, indexed timeline replay, and transactions spanning tasks, knowledge, and events. SQLite is a later storage step for those needs. Keep secrets in each provider's credential store or process environment, never in Orch history.

## Provider boundary

Each provider implements the `Executor` contract. The logical router chooses a tier; the model registry maps the tier to an enabled profile; the provider executes it. A new Codex model can be registered and weighted through the CLI. A new provider requires a dedicated adapter, authentication, usage parsing, and validation tests before its models can be enabled. Claude remains disabled until those pieces exist and the user has access.

## Known limits before a portfolio demo

- The task snapshot, attempt history, and UI event append are separate writes. A crash between them can leave different last-known states; the API presents the task snapshot as current state and the event log as history. SQLite transactions should solve this.
- The same project should have one Orch process running at a time. File locking is not implemented.
- An interrupted live task remains `running`. Inspect changes, stop the original process, and explicitly use `orch retry TASK-ID` before another run.
- Live validation uses the supplied command and any approved executable task checks. A passing check does not prove the semantic change is correct unless the checks cover it.
- Token counts are recorded when present. Read-only route proposals can estimate comparable usage with an explicitly supplied, versioned price snapshot; unknown price or missing usage blocks a proposal. Estimated cost is not historical billed cost.
- Simulated attempts must not influence real model performance recommendations.
- The current registry uses example Codex model IDs; availability depends on the signed-in account. Change the registry for your account before a live run if needed.
